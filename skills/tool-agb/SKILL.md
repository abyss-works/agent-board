# agent-board

agent-board는 프로젝트의 진행 상황과 목록형 상태(아이디어, 다음 할 일, 발견한 문제, 결정 대기)를 기록하는 트래커다. 에이전트는 `agb` CLI로 읽고 쓴다.

## 세션마다 정하는 값

- 프로젝트 키: 프로젝트 `AGENTS.md`에 적힌 트래커 프로젝트 키를 쓴다.
  - 키가 "없음"이면 이 스킬을 쓰지 않는다.
  - 키가 적혀 있는데 서버에 없으면 `agb project create <KEY> "<이름>"`으로 만든다.
- 행위자: `agb actors`에 선언된 값 중 자기 도구 이름이다. 예: `claude`, `codex`. 사람의 행위자(`owner`)는 쓰지 않는다.
- 세션 ID: 도구가 알려 주는 세션 ID를 쓴다. 모르면 세션을 시작할 때 `<행위자>-<yyyymmdd-HHMM>`을 만들어 세션 끝까지 같은 값을 쓴다.
- 행위자와 세션 ID는 모든 명령에 붙인다.
  - 셸 환경이 명령 사이에 유지되면 `AGB_ACTOR`, `AGB_SESSION_ID`를 한 번 export한다.
  - 유지되지 않으면 명령마다 옵션으로 붙인다: `agb --actor <행위자> --session-id <세션 ID> <명령>`
  - 아래 절차의 명령은 이 옵션을 생략하고 적었다.

## 접속과 로그인

에이전트는 자기 행위자의 토큰으로만 접속한다. 토큰은 기기 승인으로 받아 설정 파일에 행위자별로 저장되고, 이후 명령이 자동으로 쓴다.

- 공용 토큰(`AGB_TOKEN` 환경변수, `agb config set-token`)은 사용자 행위자 전용이다. 에이전트는 쓰지 않는다. 셸 환경에 `AGB_TOKEN`이 있으면 그 값이 먼저 쓰여 403이 나므로, 그 셸에서 해제한다(`unset AGB_TOKEN`, PowerShell은 `Remove-Item Env:AGB_TOKEN`).
- 다른 행위자의 토큰이나 `--actor`를 쓰지 않는다.
- 설정 파일의 토큰 값을 읽거나 출력하지 않는다. 토큰이 저장된 행위자는 `agb config show`의 `actor_tokens`로 본다.

### 로그인이 필요할 때

다음 중 하나가 나오면 이 행위자의 토큰이 없거나 쓸 수 없는 것이다.

- 종료 코드 2와 "토큰이 없습니다"
- 401 `unauthorized`
- 403 `forbidden`과 `details[].reason`의 `actor_mismatch`

1. 로그인을 실행한다. 사용자가 승인할 때까지 명령이 끝나지 않으므로 백그라운드로 실행하거나 시간 제한을 11분 이상으로 둔다.
   ```
   agb --actor <자기 ID> login
   ```
   - 행위자가 서버에 선언되지 않았거나 사람의 행위자이면 서버가 422로 거절한다. 이때는 로그인을 되풀이하지 않고 사용자에게 알린다.
2. 표준 오류의 승인 주소와 승인 코드를 읽어 사용자에게 알린다. 백그라운드로 실행했으면 그 출력에서 읽는다.
   ```
   승인 주소: <서버 주소>/device?code=BDFG-HJKL
   승인 코드: BDFG-HJKL
   ```
   - 사용자가 주소를 열고, 웹 화면의 코드가 같은지 확인한 뒤 승인한다. 브라우저가 자동으로 열려도 주소를 알린다. 에이전트가 사용자 화면이 없는 곳에서 실행 중일 수 있다.
   - 승인 요청은 10분 뒤 만료된다.
3. 승인을 기다린다. 승인 전에는 이 세션에서 기록할 내용(등록할 이슈, 댓글, 상태 변경)을 최종 보고에 모은다.
   - Expected: 종료 코드 0과 `{"actor":"<자기 ID>","client_host":"<기기 이름>","token_id":<번호>,"created_at":"<시각>"}`. 토큰 값은 출력되지 않는다.
4. 막혔던 명령을 다시 실행하고, 모아 둔 기록을 등록한다.
   ```
   agb whoami
   ```
   - Expected: 응답의 `id`가 자기 행위자
5. 종료 코드 1로 끝나면 stderr의 문구를 따른다.
   - "승인이 거부되었습니다.": 사용자가 거부한 것이다. 다시 로그인하지 않고 최종 보고에 알린다.
   - "승인 시간이 지났습니다. 다시 실행하세요.": 사용자에게 알린 뒤 한 번 더 실행한다.

## 출력과 종료 코드

- 출력이 파이프나 파일이면 서버 응답 JSON이 그대로 나온다. 에이전트는 JSON으로 읽는다. 사람에게 보여 줄 때만 `--table`을 붙인다.
- 종료 코드: 0 성공, 1 API·네트워크 오류, 2 사용법 오류. 1이면 stderr의 `error.code`와 `details`를 읽고 고친다.
- 인증 오류(401, 403 `actor_mismatch`, "토큰이 없습니다")는 고치려 하지 말고 "접속과 로그인"을 따른다.
- 긴 본문과 댓글은 `--body-file -`(표준 입력)이나 `--body-file <경로>`로 넘긴다. 셸 인용 때문에 내용이 바뀌지 않는다.

## 1. 세션을 시작할 때

1. 서버를 확인한다.
   ```
   agb health
   ```
   - Expected: `"status":"ok"`
   - 실패하면 "접속할 수 없을 때"를 따른다.
2. 프로젝트 현황을 본다.
   ```
   agb project overview <KEY>
   ```
   - 진행 중, 검토, 차단, 결정 대기, 다음 할 일, 미확인, 최근 활동이 나온다.
3. 이번 작업 대상을 다른 세션이 진행 중인지 확인한다.
   ```
   agb issue list -p <KEY> --status doing
   agb issue activity <ISSUE>
   ```
   - 같은 이슈를 다른 세션이 `doing`으로 두었으면 그 이슈를 맡지 않고 사용자에게 알린다.

## 2. 등록할 때

아이디어, 다음 할 일, 발견한 문제, 결정 대기는 발견한 즉시 등록한다.

1. 같은 내용이 이미 있는지 찾는다.
   ```
   agb search "<핵심어>" -p <KEY> --status all
   ```
   - 있으면 새로 만들지 않고 그 이슈에 댓글을 단다.
2. 종류를 고른다.

   | 기록할 것 | `--type` |
   |---|---|
   | 다음 할 일 | `feature`, `bug`, `design` |
   | 아이디어 | `idea` |
   | 발견했지만 지금 고치지 않는 문제 | `observation`. 다시 볼 조건 `--recheck`가 필수다 |
   | 사용자 결정 대기 | `decision` |

3. 주제를 고른다. 프로젝트의 주제 목록을 보고 맞는 주제를 `--topic`으로 붙인다.
   ```
   agb topic list -p <KEY>
   ```
   - 주제는 대주제와 그 아래 주제 두 단계다. 가장 구체적으로 맞는 주제를 고르고, 경로(`"이슈 흐름/트리아지"`)나 ID로 붙인다. 대주제만 맞으면 대주제(`"이슈 흐름"`)를 붙인다.
   - 맞는 주제가 없으면 기존 대주제 아래에 주제를 만든다.
     ```
     agb topic create -p <KEY> "<주제 이름>" --parent "<대주제>"
     ```
   - 새 대주제는 만들지 않는다. 맞는 대주제가 없으면 `--topic` 없이 등록하고, 새 대주제가 필요하다는 제안을 최종 보고에 쓴다.
4. 마일스톤을 고른다. 마일스톤은 사용자가 정한 로드맵 버전이다. 이 이슈가 들어갈 버전이 분명할 때만 붙인다.
   ```
   agb milestone list -p <KEY>
   ```
   - Expected: `items`에 열린 마일스톤의 `id`, `name`, `target_date`, `progress`가 나온다. 이 목록에 있는 마일스톤에만 이슈를 배정한다.
   - 이름(`"v0.2.0"`)이나 ID를 `--milestone`에 준다. 이름은 정확히 같아야 하고, 맞는 것이 없으면 종료 코드 2로 멈춘다.
   - 맞는 마일스톤이 없거나 어느 버전인지 알 수 없으면 `--milestone` 없이 등록한다. 마일스톤을 새로 만들지 않고, 새 마일스톤이 필요하다는 제안을 최종 보고에 쓴다.
   - 이미 등록한 이슈는 `agb issue update <ISSUE> --milestone "<이름>"`으로 배정한다.
5. 등록한다. 제목과 본문은 "이슈 템플릿"의 해당 종류를 따른다.
   ```
   agb issue create -p <KEY> -t "<제목>" --type <종류> [--topic "<대주제/주제>"] [--milestone "<이름>"] [--priority P1] [--label <라벨>] [--ref <종류:값>] --body-file - <<'EOF'
   <종류별 템플릿을 채운 본문>
   EOF
   ```
   - 우선순위를 정할 근거가 없으면 기본값(P2)으로 둔다.
   - 참조는 `종류:값`이다. 종류는 `repo`, `file`, `url`, `pr`, `issue`, `doc`이다.
   - Expected: 종료 코드 0과 새 이슈 키(`<KEY>-<번호>`)

## 3. 작업을 시작할 때

1. 맡을 이슈를 `doing`으로 바꾼다. 이슈가 없으면 2절로 먼저 등록한다.
   ```
   agb issue update <ISSUE> --status doing
   ```
   - Expected: 응답의 `status`가 `doing`. 상태 변경에 행위자와 세션 ID가 함께 남는다.
   - 상태를 바꿀 때는 `--reason "<사유>"`로 이유를 남길 수 있다. 사유는 1~500자이고 이슈의 상태 사유와 활동 기록에 남는다. 생략하면 서버가 `할 일 → 진행`처럼 이전 상태와 새 상태를 사유로 적는다. 기본 문장보다 알려야 할 이유가 있으면 직접 쓴다.

## 4. 진행 중

- 상태가 실제로 바뀔 때만 댓글을 단다. 예: 중간 결과, 범위 변경, 막힘. 같은 내용을 되풀이하지 않는다.
  ```
  agb issue comment <ISSUE> --summary "<요약>" --body-file - <<'EOF'
  <내용>
  EOF
  ```
- 댓글에는 `--summary`를 반드시 붙인다. 요약은 목록에 한 줄로 보이는 색인이다.
  - 무엇을 했는지 떠올리게 하는 명사구로 쓴다. 예: `서버 랭킹 함수 구현`, `랭킹 UI 위치 변경`
  - 15자 안팎으로 쓴다. 서버 한도는 30자이고, 줄바꿈을 넣을 수 없다.
  - 상세는 본문에 쓴다.
- 막혔다고 판단하면 원인을 확인한 근거(실행한 명령과 결과)를 댓글에 쓴다.
- 라벨, 선행 이슈, 참조를 하나씩 더하거나 뺄 때는 `--add-*`, `--remove-*`를 쓴다. 현재 값을 읽고 `If-Match`로 보내므로 다른 세션의 변경을 덮어쓰지 않는다. 412로 실패하면 `agb issue get <ISSUE>`로 다시 읽고 고친다.

## 5. 마칠 때

1. 끝난 이슈를 닫고 결과를 댓글로 남긴다. 결과에는 커밋 해시와 검증 명령의 결과를 쓴다.
   ```
   agb issue update <ISSUE> --status done
   agb issue comment <ISSUE> --summary "<요약>" --body-file - <<'EOF'
   <결과와 증거>
   EOF
   ```
   - 사용자의 확인이 필요한 결과는 `done` 대신 `review`로 둔다.
2. 결정 대기 이슈에 결정이 나면 결정 기록 파일명을 참조로 넣고 닫는다.
   ```
   agb issue update <ISSUE> --add-ref doc:<결정 기록 파일명> --status done
   ```
3. 필요 없어진 이슈는 취소한다. 취소(`cancelled`)와 삭제(`deleted`)는 사유가 필수이고, 사유가 없으면 서버가 422로 거절한다.
   ```
   agb issue update <ISSUE> --status cancelled --reason "<취소한 이유. 중복이면 원본 이슈 키>"
   ```
4. 최종 보고 전에 현황을 다시 본다.
   ```
   agb project overview <KEY>
   ```
   - 이번 작업에서 남은 이슈의 개수와 키를 보고의 결론에 쓴다.

## 이슈 템플릿

모든 종류에 공통으로 지킨다.

- 서버가 에이전트의 이슈를 검사한다. 이슈를 만들 때와, 본문이나 종류를 바꾸는 수정에서 본문에 종류별 템플릿의 `##` 제목이 순서대로 모두 있어야 한다. 빠지거나 순서가 다르면 서버가 422(`body`)로 거절하고 빠진 제목을 알려 준다.
- 템플릿은 `agb template show <종류>`로 받는다. 이 절의 템플릿과 같은 내용이 그대로 출력되므로 파일에 저장해 채운 뒤 `--body-file`로 넘긴다. `agb template list`는 종류별 제목 목록과 제목 규칙을 보여 준다.
  ```
  agb template show feature > body.md
  ```
- 본문은 종류별 템플릿의 `##` 제목을 순서대로 모두 쓴다. 제목 이름을 바꾸거나 다른 제목을 더하지 않는다.
- 쓸 내용이 없는 칸에는 `없음`을, 확인하지 못한 칸에는 `미확인`을 쓴다.
- 확인한 사실과 추정을 구분한다. 추정에는 "(추정)"을 붙인다.
- 날짜는 `2026-10-17`처럼 절대 날짜로 쓴다. 다른 이슈는 키(`AGB-2`)로, 문서는 파일명으로 가리킨다.
- 제목에 다른 체계의 번호나 꼬리표를 붙이지 않는다. 관련 번호는 본문이나 참조에 쓴다.

### 기능 (`feature`)

제목: 만들거나 바꿀 것을 명사형으로 쓴다. 예: `댓글 최신순 정렬`

```
## 배경
왜 필요한지. 요청한 사람과 날짜, 관련 결정이나 이슈.

## 할 일
- 작업 단위 하나씩

## 완료 조건
- 확인할 수 있는 조건. 실행할 명령, 볼 화면, 받을 응답.
```

### 버그 (`bug`)

제목: 잘못된 동작을 쓴다. 예: `PowerShell 파이프로 넘긴 본문의 한글이 깨짐`

```
## 현상
기대한 동작과 실제 동작.

## 재현
1. 단계
- 환경: 버전, 인스턴스, 브라우저나 셸

## 원인
확인한 원인과 근거. 모르면 `미확인`.

## 완료 조건
- 재현 절차에서 기대한 동작이 나온다.
- 회귀 테스트
```

### 설계 (`design`)

제목: 정할 대상을 쓴다. 예: `웹 정적 파일 서빙 방식`

```
## 배경
왜 지금 정해야 하는지.

## 정할 것
- 질문 하나씩

## 후보
- 후보: 장점과 단점

## 제약
지켜야 할 결정, 규칙, 환경.

## 완료 조건
- 결정 기록이나 설계 문서가 생기고 참조(`doc:`)로 연결된다.
```

### 결정 대기 (`decision`)

제목: 결정할 대상을 쓴다. 예: `운영 인스턴스의 인증 방식`

```
## 현황
결정이 필요한 이유와 지금 상태.

## 결정할 것
결정 하나를 한 문장으로.

## 선택지

## 영향
결정을 기다리는 작업(이슈 키)과 결정이 늦을 때 생기는 일.
```

### 아이디어 (`idea`)

제목: 아이디어를 명사형으로 쓴다. 예: `로컬 기록을 운영 인스턴스와 자동 동기화`

```
## 내용
아이디어를 한두 문단으로.

## 출처
누가, 언제, 어떤 논의에서 냈는지.

## 검토할 것
- 채택 전에 확인할 질문
```

### 관측 (`observation`)

제목: 관측한 현상을 쓴다. 예: `스테이징 DB에 남은 시험 데이터`. `--recheck`에 다시 볼 조건을 넣는다.

```
## 현상
확인한 사실과 근거(명령, 로그, 수치).

## 지금 고치지 않는 이유
이유. 원문에 없으면 `미확인`.

## 다시 볼 때 할 일
- 재검토 조건이 되었을 때 확인하거나 할 일
```

## 지키는 것

- 이슈와 프로젝트를 지우지 않는다. `agb issue delete`, `agb project delete`를 쓰지 않는다. 필요 없어진 이슈는 사유(`--reason`)를 붙여 `cancelled`로 바꾼다. 취소에는 사유가 필수다.
- 확인 표시(`agb issue ack`, `agb issue unack`)는 하지 않는다. 확인은 사용자의 몫이다. 에이전트가 만든 이슈는 미확인으로 시작하고, 사용자가 웹 화면에서 확인한다. 미확인이어도 상태 변경, 큐, 막힘 계산에 영향이 없으므로 작업은 그대로 진행한다.
- 마일스톤은 사용자가 정한다. 에이전트는 이슈를 배정하기만 하고 마일스톤을 새로 만들거나 고치거나 닫거나 지우지 않는다. `agb milestone create`, `update`, `close`, `reopen`, `delete`를 쓰지 않는다. 필요하다고 판단하면 최종 보고에 제안한다.
- 활동 기록은 수정 요청마다 바뀐 필드의 이전 값과 새 값을 모두 남긴다. `agb issue activity <ISSUE>`로 본다.
- 스테이징이나 테스트 서버에 기록하지 않는다. 기록은 설정 파일의 서버 하나에만 한다.

## 접속할 수 없을 때

- 등록할 항목을 최종 보고에 모으고 사용자에게 알린다. 접속되면 등록한다.
- 서버를 직접 띄우거나 다시 시작하지 않는다.

## Windows

- Git Bash의 heredoc은 UTF-8로 넘어간다.
- PowerShell 5.1에서 파이프로 본문을 넘기면 셸 인코딩 때문에 한글이 깨질 수 있다. 본문을 UTF-8 파일로 저장하고 `--body-file <경로>`로 넘긴다.
- JSON 출력을 다른 프로그램으로 읽을 때는 UTF-8로 디코딩한다.
