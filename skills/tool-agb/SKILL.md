# agent-board

agent-board는 프로젝트의 진행 상황과 목록형 상태(아이디어, 다음 할 일, 발견한 문제, 결정이 필요한 질문)를 기록하는 트래커다. 에이전트는 `agb` CLI로 읽고 쓴다.

`agb`가 설치되어 있지 않거나, 서버 주소가 설정되어 있지 않거나, CLI·스킬을 새 릴리즈로 바꿀 때는 `references/setup.md`를 따른다.

## 세션마다 정하는 값

- 프로젝트 키: 작업 중인 저장소 최상위 `.agb.json`의 `project`를 쓴다(`agb init -p <KEY>`로 만든 파일).
  - `.agb.json`이 없으면 CLI가 키를 알 수 없다. 사용자가 알려 준 키를 명령마다 `-p <KEY>`로 준다. 키를 모르면 `agb project list`로 목록을 보여 주고 사용자에게 묻는다. 키를 추측하지 않는다.
  - 키가 정해졌는데 서버에 없으면 `agb project create <KEY> "<이름>"`으로 만든다.
- 행위자: `agb actors`에 선언된 값 중 자기 도구 이름이다. 예: `claude`, `codex`. 사람의 행위자(`owner`)는 쓰지 않는다.
- 세션 ID: 도구가 알려 주는 세션 ID를 쓴다. 모르면 세션을 시작할 때 `<행위자>-<yyyymmdd-HHMM>`을 만들어 세션 끝까지 같은 값을 쓴다.
- 행위자와 세션 ID는 모든 명령에 붙인다.
  - 셸 환경이 명령 사이에 유지되면 `AGB_ACTOR`, `AGB_SESSION_ID`를 한 번 export한다.
  - 유지되지 않으면 명령마다 옵션으로 붙인다: `agb --actor <행위자> --session-id <세션 ID> <명령>`
  - 아래 절차의 명령은 이 옵션을 생략하고 적었다.

## 기록의 성격

- agb는 에이전트가 관리하는 트래커다. 사용자는 대화에서 승인만 한다.
- agb의 기록(이슈, 댓글, 상태, 마일스톤, 주제, 기록 문서)은 에이전트의 작업 공간이다. 서버에 있어도 고치기 전에 원본을 따로 보관하지 않는다.
  - 기록을 고치기 전에 원본을 로컬에 스냅샷하지 않는다. 서버의 활동 기록이 변경 이력을 남긴다.
- 기본은 에이전트 자율이다. 이슈, 댓글, 주제의 생성·수정과 상태 변경(취소 포함)은 묻지 않고 한다.
- 이슈, 프로젝트, 주제의 삭제도 자율이다. agb의 삭제는 모두 상태를 `deleted`로 바꾸는 soft delete이고 되살릴 수 있다.
  - 이슈는 사유(`--reason`)를 붙여 지운다. 되살리기: `agb issue update <KEY> --status <상태>`
  - 프로젝트 되살리기: `agb project update <KEY> --status active`
  - 주제 되살리기: `agb topic update <ID> --status active`
  - 지운 것은 최종 보고에 키와 사유를 쓴다.
- 다음 중대 결정은 질문 도구로 사용자에게 묻고, 승인받은 뒤 에이전트가 실행한다.
  - 마일스톤 범위(버전 이름과 담을 이슈) 고르기, 마일스톤 고치기, 다시 열기, 지우기. 마일스톤은 로드맵 버전이다.
  - 검토(`review`)를 완료로 받아들이는 것("5. 마칠 때").
- 마일스톤 닫기는 자율이다. 마일스톤의 이슈가 모두 닫혔고 그 버전이 릴리즈됐을 때 `agb milestone close <ID>`로 닫는다.
- 마일스톤 만들기는 사용자가 범위를 고른 뒤 에이전트가 `agb milestone create`로 하고, 고른 이슈를 배정한다.
- agb 서버 자체(배포, 데이터베이스, 백업, 서버 설정)는 운영 자원이다. 이 스킬의 명령으로 다루지 않는다. 바꿔야 하면 사용자에게 알린다.

## 접속과 로그인

에이전트는 자기 행위자의 토큰으로만 접속한다. 토큰은 기기 승인으로 받아 설정 파일에 행위자별로 저장되고, 이후 명령이 자동으로 쓴다.

- 공용 토큰(`AGB_TOKEN` 환경변수, `agb config set-token`)은 사용자 행위자 전용이다. 에이전트는 쓰지 않는다. `agb login`으로 받은 행위자별 토큰이 설정 파일에 있으면 그 토큰이 `AGB_TOKEN`보다 먼저 쓰이므로 환경변수를 해제할 필요가 없다. 행위자별 토큰이 없는 상태에서 `AGB_TOKEN`이나 공용 토큰이 쓰여 403이 나면, 그 셸에서 `AGB_TOKEN`을 해제하고(`unset AGB_TOKEN`, PowerShell은 `Remove-Item Env:AGB_TOKEN`) `agb login`을 한다.
- 다른 행위자의 토큰이나 `--actor`를 쓰지 않는다.
- 설정 파일의 토큰 값을 읽거나 출력하지 않는다. 토큰이 저장된 행위자는 `agb config show`의 `actor_tokens`로 본다.

### 로그인이 필요할 때

다음 중 하나가 나오면 이 행위자의 토큰이 없거나 쓸 수 없다.

- 종료 코드 2와 "토큰이 없습니다"
- 401 `unauthorized`
- 403 `forbidden`과 `details[].reason`의 `actor_mismatch`

1. 로그인을 실행한다. 사용자가 승인할 때까지 명령이 끝나지 않으므로 백그라운드로 실행하거나 시간 제한을 11분 이상으로 둔다.
   ```
   agb --actor <자기 ID> login
   ```
   - 행위자가 서버에 선언되지 않았거나 사람의 행위자이면 서버가 422로 거절한다. 이때는 로그인을 되풀이하지 않고 사용자에게 알린다.
2. 표준 오류의 승인 주소와 승인 코드를 읽어 사용자에게 알린다. 백그라운드로 실행했으면 그 출력에서 읽는다.
   ```
   승인 주소: <서버 주소>/device?code=BDFG-HJKL
   승인 코드: BDFG-HJKL
   ```
   - 사용자가 주소를 열고, 웹 화면의 코드가 같은지 확인한 뒤 승인한다. 브라우저가 자동으로 열려도 주소를 알린다. 에이전트가 사용자 화면이 없는 곳에서 실행 중일 수 있다.
   - 승인 요청은 10분 뒤 만료된다.
3. 승인을 기다린다. 승인 전에는 이 세션에서 기록할 내용(등록할 이슈, 댓글, 상태 변경)을 최종 보고에 모은다.
   - Expected: 종료 코드 0과 `{"actor":"<자기 ID>","client_host":"<기기 이름>","token_id":<번호>,"created_at":"<시각>"}`. 토큰 값은 출력되지 않는다.
4. 막혔던 명령을 다시 실행하고, 모아 둔 기록을 등록한다.
   ```
   agb whoami
   ```
   - Expected: 응답의 `id`가 자기 행위자
5. 종료 코드 1로 끝나면 stderr의 문구를 따른다.
   - "승인이 거부되었습니다.": 사용자가 거부했다. 다시 로그인하지 않고 최종 보고에 알린다.
   - "승인 시간이 지났습니다. 다시 실행하세요.": 사용자에게 알린 뒤 한 번 더 실행한다.

## 출력과 종료 코드

- 출력이 파이프나 파일이면 서버 응답 JSON이 그대로 나온다. 에이전트는 JSON으로 읽는다. 사람에게 보여 줄 때만 `--table`을 붙인다.
- agb의 JSON을 스크립트(python, jq, sed 등)로 가공하지 않는다. 필요한 값은 `--fields`로 고르고, 줄 단위로 읽을 때는 `--text`를 더한다. 옵션의 규칙은 `agb --help`가 정본이다.

  | 필요한 것 | 명령 |
  |---|---|
  | 이슈 목록의 키, 상태, 제목 | `agb issue list -p <KEY> --fields key,status,title --text` |
  | 이슈 본문 원문 | `agb issue get <KEY> --fields body --text` |
  | 이슈 활동 행(종류, 작성자, 시각, 본문). 댓글은 `kind`가 `commented`인 행 | `agb issue activity <KEY> --fields kind,actor,at,body --text` |
  | 기록 문서 동기화 요약 | `agb doc sync --fields uploaded,conflicts,rejected --text` |
  | 기록 문서 검사의 문제 | `agb doc check --fields files.name,files.problems --text` |
- 종료 코드: 0 성공, 1 API·네트워크 오류, 2 사용법 오류. 1이면 stderr의 `error.code`와 `details`를 읽고 고친다.
- 인증 오류(401, 403 `actor_mismatch`, "토큰이 없습니다")는 고치려 하지 말고 "접속과 로그인"을 따른다.
- 긴 본문과 댓글은 `--body-file -`(표준 입력)이나 `--body-file <경로>`로 넘긴다. 셸 인용 때문에 내용이 바뀌지 않는다.

## 1. 세션을 시작할 때

1. CLI, 서버, 스킬의 판을 맞춘다. 스킬 폴더(`~/.agents/skills/tool-agb`)가 링크(정션, 심볼릭 링크)인지에 따라 다르다.
   - 복사본이면 스킬을 CLI와 같은 릴리즈로 맞춘다. 같으면 아무것도 바꾸지 않는다.
     ```
     agb skill install
     ```
     - Expected: `변경 없음: ...` 또는 `설치했습니다: ...`
     - `설치했습니다`가 나오면 이 스킬을 다시 읽고 이어 간다.
   - 링크이면 `agb skill install`을 실행하지 않는다. 링크를 지우고 복사본으로 바꾸기 때문이다. 점검만 한다.
     ```
     agb skill check
     ```
     - Expected: 종료 코드 0. `CLI ...: 같음`(또는 비교를 건너뛴다는 안내)과 `스킬: 같음 (...)`이 나온다. 아무것도 바꾸지 않는다.
     - 종료 코드 1이면 다음 중 하나다.
       - `CLI가 서버보다 오래됐습니다`: 출력된 `갱신:` 명령으로 CLI를 다시 설치한다(`references/setup.md` 1절).
       - `내장된 스킬과 다릅니다`: 스킬이 이 CLI와 다른 판이다. 스킬에 적힌 명령이 CLI에 없을 수 있으므로 적히지 않은 명령을 쓰지 않는다. 링크가 저장소를 가리키면 그 브랜치에서 CLI를 다시 설치하거나, `agb skill show`로 이 CLI에 맞는 본문을 읽는다.
       - `설치되어 있지 않습니다`: `agb skill install`로 설치한다.
   - `agb: 모르는 명령 "skill"`이 나오면 CLI가 옛 판이다. `references/setup.md` 1절로 CLI를 다시 설치한다.
   - 에이전트 도구가 `~/.agents/skills`가 아닌 폴더의 스킬을 읽으면 두 명령 모두 `--dir <그 폴더>`를 준다.
2. 서버를 확인한다.
   ```
   agb health
   ```
   - Expected: `"status":"ok"`
   - 실패하면 "접속할 수 없을 때"를 따른다.
3. 프로젝트의 할 일을 본다.
   ```
   agb agenda -p <KEY>
   ```
   - 사용자 차례(검토, 결정 필요, 미확인, 사용자 할 일), 에이전트(진행 중, 다음 할 일), 대기(막힘, 외부 대기)가 나온다. `user-task`와 `external` 이슈는 다음 할 일에 나오지 않는다. 옵션은 `agb agenda --help`.
   - 오래됨 개수가 0이 아니면 `agb issue list --dormant`로 본다. 30일 넘게 활동이 없는 열린 이슈이며 표시일 뿐 자동으로 닫히지 않으니, 닫을지는 사용자와 판단할 대상으로 본다.
   - 분포와 최근 활동까지 보려면 `agb project overview <KEY>`를 쓴다.
   - 같은 세션을 며칠 뒤 다시 쓰거나 컨텍스트가 압축된 뒤에도 이 절차로 현황을 다시 본다. 어느 시점 이후 바뀐 것(사용자의 "리마인드", "지난번 이후 뭐 했지", 다른 기기나 세션의 작업)은 `agb digest --since <시점> [-p <KEY>]`로 본다. 새 이슈, 상태 변경, 결정 요청, 등록된 기록 문서가 프로젝트별로 나온다. 시점 형식은 `agb digest --help`. `activity`를 여러 번 불러 스크립트로 집계하지 않는다.
   - 세션을 시작할 때는 검토, 결정 필요, 미확인을 사용자에게 묻지 않는다. 이번 작업에 걸린 항목은 그 이슈를 맡을 때(3절 2)와 최종 보고 전(5절 3)에 "사용자 차례"를 따라 묻는다.
4. 이번 작업 대상을 다른 세션이 진행 중인지 확인한다. 3의 진행 중 항목의 `holder`를 본다.
   - `holder`는 그 이슈를 진행으로 옮긴 세션이다. `actor`, `session_id`, `last_active_at`(그 세션이 어느 이슈에든 남긴 마지막 기록), `stale`(마지막 기록에서 2시간이 지남)이 있다.
   - 다른 세션이 점유했고 `stale`이 `false`이면 그 이슈를 맡지 않는다. 다른 이슈를 고르고, 그 이슈가 꼭 필요하면 사용자에게 알린다.
   - 이어받거나 이어 갈 진행 중 이슈는 `agb issue get <ISSUE>`로 연다. 표 출력 끝의 "마지막 작업 위치"에 그 이슈를 어느 호스트의 어느 브랜치·워크트리에서 어디까지 했는지가 나온다. 다른 호스트에서 남긴 기록이면 커밋하지 않은 변경은 그 호스트에만 있으므로, 원격에 푸시된 작업 브랜치만 이어받고 나머지는 사용자에게 알린다.
   - 다른 세션이 점유했고 `stale`이 `true`이면 이어받을 수 있다. 백로그로 되돌린 뒤 다시 진행으로 옮기고, 두 변경 모두 사유를 남긴다.
     ```
     agb issue update <ISSUE> --status backlog --reason "<이전 세션 ID>의 점유가 멈춰 이어받음"
     agb issue update <ISSUE> --status doing --reason "멈춘 점유 이어받음"
     ```

## 2. 등록할 때

1. 같은 내용이 이미 있는지 찾는다.
   ```
   agb search "<핵심어>" -p <KEY> --status all
   ```
   - 있으면 새로 만들지 않고 그 이슈에 댓글을 단다.
2. 목록형 상태(다음 할 일, 발견한 문제, 결정이 필요한 질문, 아이디어)를 agb의 종류와 표시로 옮긴다.

   | 목록형 상태 | agb |
   |---|---|
   | 다음 할 일 | `--type feature`, `bug`, `design` |
   | 아이디어 | `--type idea` |
   | 발견했지만 지금 고치지 않는 문제 | `--type observation`. 다시 볼 조건 `--recheck`가 필수다 |
   | 미결 결정 | 종류가 아니다. 그 결정이 걸린 이슈에 `--decision-needed "<질문>"`으로 남긴다(3절 "결정 필요 표시") |

3. 주제를 고른다. 프로젝트의 주제 목록을 보고 맞는 주제를 `--topic`으로 붙인다.
   ```
   agb topic list -p <KEY>
   ```
   - 주제는 대주제와 그 아래 주제 두 단계다. 가장 구체적으로 맞는 주제를 고르고, 경로(`"이슈 흐름/트리아지"`)나 ID로 붙인다. 대주제만 맞으면 대주제(`"이슈 흐름"`)를 붙인다.
   - 맞는 주제가 없으면 기존 대주제 아래에 주제를 만든다.
     ```
     agb topic create -p <KEY> "<주제 이름>" --parent "<대주제>"
     ```
   - 맞는 대주제가 없으면 대주제를 만들고 그 아래에 주제를 만든다. 만든 대주제는 최종 보고에 쓴다.
     ```
     agb topic create -p <KEY> "<대주제 이름>"
     ```
4. 마일스톤을 고른다. 마일스톤은 사용자가 정한 로드맵 버전이다. 이 이슈가 들어갈 버전이 분명할 때만 붙인다.
   ```
   agb milestone list -p <KEY>
   ```
   - Expected: `items`에 열린 마일스톤의 `id`, `name`, `target_date`, `progress`가 나온다. 이 목록에 있는 마일스톤에만 이슈를 배정한다.
   - 이름(`"v0.2.0"`)이나 ID를 `--milestone`에 준다. 이름 규칙은 `agb issue create --help`.
   - 맞는 마일스톤이 없거나 어느 버전인지 알 수 없으면 `--milestone` 없이 등록한다. 새 마일스톤이 필요하다고 판단하면 질문 도구로 사용자에게 범위(버전 이름과 담을 이슈)를 고르게 하고, 고른 뒤 `agb milestone create`로 먼저 만들고 `--milestone`으로 붙인다.
   - 이미 등록한 이슈는 `agb issue update <ISSUE> --milestone "<이름>"`으로 배정한다.
5. 등록한다. 제목과 본문은 "이슈 템플릿"의 해당 종류를 따른다.
   ```
   agb issue create -p <KEY> -t "<제목>" --type <종류> [--topic "<대주제/주제>"] [--milestone "<이름>"] [--priority <P0~P3>] [--label <라벨>] [--ref <종류:값>] --body-file - <<'EOF'
   <종류별 템플릿을 채운 본문>
   EOF
   ```
   - 제목은 종류별 형식으로 쓴다.

     | 종류 | 형식 | 예 |
     |---|---|---|
     | `feature` | `<사용자>는 <무엇>을 할 수 있다` | 사용자는 검색 결과를 CSV로 내보낼 수 있다 |
     | `bug` | `<위치>에서 <현상> 문제 수정` | 로그인 화면에서 비밀번호 재설정 메일이 오지 않는 문제 수정 |
     | `design` | `<주제> 결정` | 이슈 제목 작성 형식 결정 |
     | `idea` | `<무엇> 검토` | 알림 묶음 발송 검토 |
     | `observation` | `<대상>의 <현상> 관찰` | 야간 배치의 알림 중복 발송 관찰 |

   - 제목은 50자를 넘기지 않는다.
   - 제목에 이슈 키, 날짜, 내부 용어를 쓰지 않는다. 원인과 경위는 본문에 쓴다.
   - 우선순위는 이슈가 미치는 영향으로 정한다. 누가 등록했는지, 누가 시켰는지로 정하지 않는다. 사용자가 우선순위를 말하면 그것을 따른다. 말하지 않았으면 아래 조건을 위에서부터 확인해 처음 맞는 등급으로 정한다. 점수를 매기거나 느낌으로 올리고 내리지 않는다.

     | 등급 | 조건 |
     |---|---|
     | `P0` | 종류와 무관하게 운영 장애, 데이터 손실, 보안 결함이다 |
     | `P1` | P0이 아닌 `bug`다 |
     | `P3` | P0이 아닌 `idea`나 `observation`이다. 또는 사용자가 미뤘다 |
     | `P2` | 그 밖의 종류다. 예: `feature`, `design` |

   - `P0`은 위 세 경우에만 쓴다. 작업 순서를 나타내는 데 쓰지 않는다. 서버는 `P0`을 자동으로 매기지 않으므로 `--priority P0`을 직접 준다.
   - `--priority`를 생략하면 서버가 종류로 `bug`는 `P1`, `idea`·`observation`은 `P3`, 그 밖에는 `P2`를 넣는다. 행위자 종류와 무관하다. 사용자가 우선순위를 말했거나 `P0`에 해당하면 `--priority`를 준다.
   - 조건이 바뀌면 등급을 고친다. 예: 장애가 해소되면 `P0`에서 `P1`로 내린다.
   - 같은 등급 안의 순서는 서버가 정한다(선행 이슈 완료, 열린 마일스톤, 막고 있는 이슈 수, 생성 순서).
   - 참조는 `종류:값`이다. 종류 목록은 `agb issue create --help`.
     - 팀 트래커와 팀 결정은 형식 있는 참조로 붙인다. 예: `jira:S15P31A308-261`, `mr:164`, `adr:ADR-0013`. 본문 문장에만 쓰지 않는다.
     - 참조로 이슈를 찾을 때는 `agb issue list --ref <종류:값>`을 쓴다.
   - Expected: 종료 코드 0과 새 이슈 키(`<KEY>-<번호>`)

## 3. 작업을 시작할 때

1. 맡을 이슈를 `backlog`에서 `doing`으로 바꾼다. 이슈가 없으면 2절로 먼저 등록한다.
   ```
   agb issue update <ISSUE> --status doing
   ```
   - Expected: 응답의 `status`가 `doing`. 상태 변경에 행위자와 세션 ID가 함께 남는다.
   - 저장소에서 작업 브랜치를 만들어 일하면, 브랜치와 워크트리를 만든 뒤 상태를 바꾸면서 작업 위치를 남긴다. 마칠 때 CLI가 이 기록의 저장소와 브랜치로 병합 커밋을 찾는다(5절 1).
     ```
     agb issue comment <ISSUE> --status doing --summary "착수" --repo <작업 워크트리> --body "<할 일 한 줄>"
     ```
   - 상태를 바꿀 때는 `--reason "<사유>"`로 이유를 남길 수 있다. 생략하면 서버가 이전 상태와 새 상태를 사유로 적는다. 기본 문장보다 알려야 할 이유가 있으면 직접 쓴다(`agb issue update --help`).
2. 이슈에 결정 필요 표시(`decision_needed`)가 있으면 작업 전에 사용자에게 질문 도구로 묻는다. 사용자가 웹 댓글로 답하기를 기다리지 않는다.
   - 답을 받으면 결정 내용을 이슈 댓글에 적는다. 결정이 바꾸는 명세나 원칙 문서가 있으면 그 문서에 반영하고 참조로 붙인다. 그다음 표시를 해제한다.
     ```
     agb issue comment <ISSUE> --kind decision --summary "<결정 요약>" --body-file - <<'EOF'
     <질문, 사용자의 답, 반영할 내용>
     EOF
     agb issue update <ISSUE> [--add-ref doc:<반영한 문서 파일명>] --decision-needed none
     ```
   - 답을 받지 못하면 표시를 그대로 두고 그 이슈의 작업을 진행하지 않는다.

### 결정 필요 표시

사용자의 답이 필요한 질문을 그 자리에서 해결하지 못하고 세션을 넘겨야 할 때만 남긴다.

- 사용자와 대화 중이면 먼저 질문 도구로 묻고, 답을 반영해 등록하거나 진행한다. 이때는 표시를 남기지 않는다.
- 질문은 결정 하나를 한 문장으로 쓴다. 선택지와 추천은 본문이나 댓글에 쓴다.
  ```
  agb issue update <ISSUE> --decision-needed "<질문>"
  ```
- 작업 도중 새 질문이 생겨 답을 받지 못한 채 멈추면 표시를 남기고 상태는 `doing`에 둔다.

### 결정을 미룰 때

사용자가 질문에 "보류", "나중에"처럼 결정을 미루면 표시를 남겨 두지 않는다. 결정 필요 표시는 사용자가 지금 답해야 하는 질문만 가리킨다.

1. 질문, 사용자의 답, 미룬 이유, 다시 볼 조건을 댓글로 남긴다. 다시 볼 조건은 판정할 수 있게 쓴다. 맞는 예: "ABC-37 알림 개편이 완료되면". 틀린 예: "나중에".
   ```
   agb issue comment <ISSUE> --kind decision --summary "사용자 결정: 보류" --body-file - <<'EOF'
   질문: <질문>
   사용자의 답(<yyyy-mm-dd>): <답>
   미룬 이유: <이유>
   다시 볼 조건: <조건>
   EOF
   ```
2. 표시를 지우고 우선순위를 `P3`로 내린다.
   ```
   agb issue update <ISSUE> --decision-needed none --priority P3
   ```
3. 다시 볼 조건이 되면(그 조건의 이슈를 마칠 때, 사용자가 그 주제를 꺼낼 때) 질문 도구로 다시 묻는다.

## 4. 진행 중

- 상태가 실제로 바뀔 때만 댓글을 단다. 예: 중간 결과, 범위 변경, 막힘. 같은 내용을 되풀이하지 않는다.
  ```
  agb issue comment <ISSUE> --summary "<요약>" --body-file - <<'EOF'
  <내용>
  EOF
  ```
- 댓글에는 `--summary`를 반드시 붙인다. 요약은 목록에 한 줄로 보이는 색인이다.
  - 무엇을 했는지 떠올리게 하는 명사구로 쓴다. 예: `서버 랭킹 함수 구현`, `랭킹 UI 위치 변경`
  - 15자 안팎으로 쓴다.
  - 상세는 본문에 쓴다.
- 결정, 발견, 교훈을 남기는 댓글에는 `--kind`로 종류를 붙인다. 종류는 나중에 진행 기록과 구분해 찾기 위한 색인이다. 진행 기록(착수, 중간 결과, 작업 위치, 완료 보고)에는 붙이지 않는다.

  | 종류 | 붙이는 댓글 |
  |---|---|
  | `decision` | 사용자나 에이전트가 정한 것과 그 이유. 기각한 대안이 있으면 함께 쓴다 |
  | `finding` | 작업 중 확인한 사실. 예: 외부 API의 실제 동작, 원인을 확인한 결함 |
  | `lesson` | 다음 작업에서 다르게 할 것. 예: 실수의 원인과 피하는 방법, 사용자에게 받은 교정 |

  ```
  agb issue comment <ISSUE> --kind finding --summary "<요약>" --body-file - <<'EOF'
  <확인한 사실과 근거(실행한 명령과 결과)>
  EOF
  ```
  - 이 이슈가 끝난 뒤에도 다른 작업의 근거가 될 결정(구조, 규칙, 범위를 정한 결정)은 저장소의 `decision` 기록 문서로 쓰고, 이슈에 참조로 건다(`agb issue update <ISSUE> --add-ref doc:<기록 문서 이름>`). 댓글에는 결정 요약과 기록 문서 이름만 쓴다.
  - 사고가 났으면 원인과 교훈을 `incident` 기록 문서로 쓰고 같은 방식으로 참조를 건다. `lesson` 댓글은 기록 문서로 쓸 만큼 크지 않은 교훈에만 쓴다.
- 막혔다고 판단하면 원인을 확인한 근거(실행한 명령과 결과)를 댓글에 쓴다.
- 작업을 멈출 때(이슈를 마치지 못하고 중단했을 때, 사용자 결정을 기다리게 됐을 때, 다른 이슈로 옮길 때)는 그 진행 중 이슈에 작업 위치를 붙인 댓글을 남긴다. 세션은 명시적으로 끝나지 않고 이어 쓰이므로 세션 종료를 계기로 삼지 않는다. CLI가 호스트와 저장소별 브랜치, HEAD, 원격과의 차이, 커밋하지 않은 파일 이름, 워크트리를 모아 붙인다. 본문에는 끝난 것, 남은 것, 마지막 검증 결과, 띄워 둔 프로세스처럼 git이 모르는 것만 쓴다.
  ```
  agb issue comment <ISSUE> --location --summary "<멈춘 지점>" --body-file - <<'EOF'
  <끝난 것, 남은 것, 마지막 검증 결과, 띄워 둔 프로세스>
  EOF
  ```
  - 기본은 현재 폴더의 저장소 하나다. 작업한 저장소가 더 있으면 저장소마다 `--repo <폴더>`를 주거나 `.agb.json`의 `location.repos`에 적어 둔다(`agb issue comment --help`, `agb help repo-config`). `location` 키는 모든 기기의 CLI를 이 키가 있는 판 이상으로 갱신한 뒤에 넣는다. 옛 CLI는 `.agb.json`의 알 수 없는 키를 거절한다.
- 여러 이슈를 볼 때는 키를 함께 준다(`agb issue get <KEY> <KEY>...`). 필드 몇 개만 필요하면 `--fields key,status,title --text`처럼 고른다. JSON을 스크립트로 가공하지 않는다("출력과 종료 코드").
- 명령 이름을 틀리면 CLI가 "가까운 명령"을 알려 준다. 그대로 다시 부른다.
- 라벨, 선행 이슈, 참조를 하나씩 더하거나 뺄 때는 `--add-*`, `--remove-*`를 쓴다. 현재 값을 읽고 `If-Match`로 보내므로 다른 세션의 변경을 덮어쓰지 않는다. 412로 실패하면 `agb issue get <ISSUE>`로 다시 읽고 고친다.

### 외부를 기다릴 때

팀원의 MR, 팀 합의, 외부 서비스처럼 agb 밖의 일을 기다려야 진행할 수 있으면, 그 일을 대신하는 이슈를 세우고 선행 이슈로 건다. 사용자가 결정을 미룬 것은 여기에 해당하지 않는다("결정을 미룰 때"를 따른다).

1. 기다리는 대상을 제목으로 하고 라벨 `external`을 단 이슈를 만든다. 대상의 키나 주소는 참조로 붙이고, 무엇이 되면 끝나는지 본문에 쓴다.
   ```
   agb issue create -p <KEY> -t "<기다리는 대상>" --label external --ref url:<MR·티켓 주소> --body-file - <<'EOF'
   <종류별 템플릿. "완료 조건"에 기다림이 끝나는 조건을 쓴다>
   EOF
   ```
2. 기다리는 이슈에 선행 이슈로 건다.
   ```
   agb issue update <ISSUE> --add-depends-on <외부 대기 이슈>
   ```
   - 기다리는 이슈는 현황의 막힘 칸에 보인다. `external` 이슈는 우선순위 큐와 다음 할 일에 나오지 않는다.
3. 세션을 시작하거나 막힌 이슈를 다시 볼 때 대상의 상태를 확인한다. 끝났으면 `external` 이슈를 `done`으로 옮긴다. 막혔던 이슈가 다음 할 일로 돌아온다.

## 5. 마칠 때

1. 끝난 이슈를 닫고 결과를 댓글로 남긴다. 결과에는 커밋 해시와 검증 명령의 결과를 쓴다.
   ```
   agb issue comment <ISSUE> --status done --summary "<요약>" --body-file - <<'EOF'
   <결과와 증거>
   EOF
   ```
   - `issue comment --status <S> [--reason <사유>]`는 상태를 바꾼 뒤 댓글을 단다. 상태 변경과 결과 댓글은 이 한 명령으로 한다.
   - 작업 브랜치를 통합 브랜치에 병합한 뒤, 병합한 저장소에서(또는 `--repo <그 저장소>`로) 부른다. `--status done`은 이슈의 작업 위치 댓글에 남은 저장소와 브랜치로 병합 커밋을 찾아 참조(`commit:`)로 붙이고, 병합과 커밋 목록을 댓글 끝에 붙인다. 결과 댓글에 커밋 목록을 다시 쓰지 않는다.
     - "병합 커밋을 찾지 못했습니다" 경고가 나오면 병합 커밋 해시를 결과 댓글에 직접 쓴다.
   - `.agb.json`에서 `auto_sync`를 켠 저장소 안에서 부르면 `agb agenda`처럼 커밋한 기록 문서 중 서버에 없는 것을 올린다("기록 문서").
   - 작업이 끝났고 다음 중 하나가 남았을 때만 `done` 대신 `review`로 둔다. 그 밖에는 결과를 댓글로 남기고 `done`으로 옮긴다.
     - 사용자가 화면이나 실기기에서 확인해야 하는 결과가 있다.
     - 사용자 승인이 필요한 다음 단계가 있다. 예: 릴리즈, 운영 반영, 원격 삭제.
     - 결과나 범위가 합의한 명세와 달라졌다.
   - `review`는 사용자에게 결과를 받아들일지 물을 때만 쓴다. 사용자가 직접 해야 하는 일(메일 수신 확인, 외부 콘솔 설정, 계정 작업)이 남았으면 `review`로 두지 않는다. 그 일을 라벨 `user-task`를 단 별도 이슈로 등록하고, 에이전트 몫이 끝난 원래 이슈는 `done`으로 옮긴다.
     ```
     agb issue create -p <KEY> -t "<사용자가 할 일>" --label user-task --ref issue:<원래 이슈> --body-file - <<'EOF'
     <종류별 템플릿. "할 일"에는 사용자가 그대로 따라 할 수 있는 단계와 기대 결과를 쓴다>
     EOF
     ```
     - 등록한 `user-task` 이슈는 최종 보고의 사용자가 할 일에 키, 제목, 절차를 함께 쓴다. 사용자가 대화에서 했다고 답하면 에이전트가 `done`으로 옮긴다.
   - `review`를 `done`으로 옮기는 것은 사용자다. 사용자가 대화에서 받아들인다고 답했을 때만 에이전트가 옮긴다. 받아들이지 않으면 `doing`으로 되돌린다.
2. 필요 없어진 이슈는 취소한다. 취소(`cancelled`)와 삭제(`deleted`)는 사유가 필수이고, 사유가 없으면 서버가 422로 거절한다.
   ```
   agb issue update <ISSUE> --status cancelled --reason "<취소한 이유. 중복이면 원본 이슈 키>"
   ```
3. 최종 보고 전에 할 일을 다시 본다.
   ```
   agb agenda -p <KEY>
   ```
   - 이번 작업에서 남은 이슈의 개수와 키를 보고의 결론에 쓴다.
   - 그다음 "사용자 차례"를 따른다.
   - 사용자와 대화 중인 세션이면 보고에 키, 제목, 내용을 적은 이슈를 보고하면서 확인 표시한다.
     ```
     agb issue ack <ISSUE>...
     ```

## 사용자에게 말할 때

사용자는 웹 화면을 열지 않고 대화로 답하고 승인한다. 웹 화면은 사용자가 현황을 둘러보는 용도다. agb 항목을 사용자에게 묻거나 알리는 모든 경우(사용자 차례, 결정 필요, 마일스톤 범위 선택, 착수할 이슈 제안, 최종 보고)에 다음을 지킨다.

- 이슈를 가리킬 때 키만 쓰지 않는다. 키와 제목, 그 이슈가 무엇을 하는지 한 문장을 함께 쓴다.
  - 맞는 예: "AGB-31 막힘 경과 시간 강조: 현황 화면 막힘 칸에 막힌 지 얼마나 지났는지 보이고 24시간이 넘으면 강조한다. 이대로 진행할까요?"
  - 틀린 예: "AGB-31 진행해도 될까요?"
- 사용자가 웹 화면이나 이슈 본문을 열어 봐야 답할 수 있는 질문을 하지 않는다. 답하는 데 필요한 내용(할 일, 완료 조건, 결과, 결과를 볼 곳)을 질문 안에 옮긴다.
- 사용자에게 웹 화면에서 처리해 달라고 요청하지 않는다. 확인 표시, 검토 수락, 결정 답변, 댓글은 대화에서 받아 에이전트가 반영한다. 예외는 기기 승인("로그인이 필요할 때")이다.

## 사용자 차례

사용자가 처리할 agb 항목(검토, 결정 필요, 미확인)을 대화에서 질문 도구로 묻고, 답을 agb에 반영하는 절차다.

### 언제

- 최종 보고 전에 현황을 다시 본 뒤(5절 3)
- 사용자가 현황이나 남은 일을 물을 때

### 모으기

`agb agenda -p <KEY>`의 사용자 차례(`user_turn`)에서 모은다. 여러 프로젝트를 함께 물을 때는 `-p`에 쉼표로 잇는다.

| 칸 | 사용자에게 묻는 것 |
|---|---|
| `review` | 결과를 받아들일지 |
| `decisions` | 이슈의 `decision_needed` 질문 |
| `unacknowledged` | 등록된 이슈를 확인했는지 |

- 최종 보고 전에는 이번 세션에서 만들었거나 맡았거나 상태를 바꾼 이슈만 묻는다.
- 그 밖의 항목은 묻지 않고 보고에 칸별 개수를 한 줄로 쓴다. 예: `남은 사용자 차례(AGB): 검토 2, 결정 필요 1, 미확인 3`
- 사용자가 현황이나 남은 일을 물으면 그 프로젝트의 항목을 모두 묻는다.
- 이번 대화에서 이미 답을 받은 항목은 다시 묻지 않는다.
- 항목이 없으면 묻지 않고 보고에 "사용자 차례 없음"이라고 쓴다.

### 묻기

질문 도구로 묻는다. 질문 형식은 "사용자에게 말할 때"를 따르고, agb 항목에는 다음을 더한다.

- 선택지마다 사용자가 결과를 어디서 볼 수 있는지 적는다. 예: 운영에 배포됨, 통합 브랜치에만 있음.
- 검토와 확인은 칸마다 여러 항목을 고르는 질문 하나로 묻는다.
  - 선택지 하나에 이슈 하나를 둔다. 같은 결정으로 함께 만든 이슈는 한 선택지로 묶는다.
  - 고르지 않은 항목은 그대로 둔다는 것을 질문에 적는다.
- 결정 필요는 이슈마다 질문 하나로 묻는다. 선택지와 추천은 그 이슈의 본문과 댓글에서 가져온다.
- 질문이나 선택지가 도구 한도를 넘으면 우선순위가 높은 이슈부터 묻고, 나머지는 답을 반영한 뒤 이어서 묻는다.

### 반영

| 답 | 반영 |
|---|---|
| 검토를 받아들임 | `agb issue update <ISSUE> --status done --reason "사용자 검토 수락(<yyyy-mm-dd>)"` |
| 검토를 받아들이지 않음 | `agb issue update <ISSUE> --status doing --reason "<사용자가 말한 이유>"` |
| 결정에 답함 | 3절 2의 절차(댓글, 문서 반영, 표시 해제) |
| 결정을 미룸 | 3절 "결정을 미룰 때"의 절차(댓글, 표시 해제, `P3`) |
| 확인함 | `agb issue ack <ISSUE>...` |
| 고르지 않음 | 그대로 둔다 |

- 사용자가 이번 대화에서 답한 이슈는 확인한 것으로 보고 함께 `ack`한다.
- 반영한 뒤 보고에 바꾼 이슈 키와 새 상태, 남은 사용자 차례의 개수를 쓴다.

## 기록 문서

판단할 때 참고하는 선례와 근거(결정, 사고, 보고, 구현 기록, 조사 자료)를 서버에 원본 그대로 보존하고 검색하는 절차다. 에이전트가 따라야 하는 규범(규칙, 명세, 스킬)은 파일이 정본이므로 올리지 않는다.

- 어떤 저장소가 agb를 지식 저장소로 쓰는지는 저장소 최상위의 `.agb.json`이 정한다. 파일이 있는 저장소에서만 CLI가 문서를 자동으로 올린다. 없으면 자동으로 올리지 않고, 올리려면 `agb doc put <파일> -p <KEY>`로 하나씩 올린다.
- 프로젝트 키(`<KEY>`)는 `.agb.json`의 `project`다. 아래 명령은 `.agb.json`이 있는 저장소 안에서 `-p`를 생략한다.
- 서버의 기록 문서는 원문을 고치거나 지울 수 없다. 같은 이름에 다른 원문을 올리면 서버가 409(`immutable`)로 거절한다. 덮어쓰려 하지 않는다. 올린 뒤에는 아카이브 표시와 관계만 고친다.
- 문서의 형식, 메타데이터, 상태, 참조 표기, 오류 코드, 형식에 맞지 않는 문서를 올리는 법은 `agb help doc-format`, `.agb.json`의 키·규칙·스키마와 예시는 `agb help repo-config`, v0.8에서 옮겨 오는 절차는 `agb help migrate-v0.8`이 정본이다. 무엇을 올릴지 정하는 규칙은 `references/documents.md`를 따른다. 다음 중 하나이면 먼저 읽는다.
  - 서버가 문서를 거절했거나 경고했을 때
  - 형식이 맞지 않는 문서나 이전 체계의 문서를 올릴 때
  - `.agb.json`을 새로 쓰거나 고칠 때
  - 올린 문서를 아카이브로 돌리거나 관계를 고칠 때
- 서버에 무엇이 있는지는 `agb doc list -p <KEY>`로 본다. 대체됨과 아카이브까지 보려면 `--state all`을 붙인다.

### 후속 항목이 나왔을 때

새로 올린 기록 문서에 `.agb.json`의 `follow_up_headings`에 적은 제목이 든 절이 있으면 CLI가 그 항목을 `후속 항목:`(자동 등록, `doc put`)이나 `follow_ups`(`doc sync`)로 알린다. CLI는 이슈를 만들지 않는다. 가져온 문서는 알리지 않는다.

- 항목마다 이슈로 추적할 일인지 정한다. 다시 해야 하거나 확인해야 하는 일이면 2절로 등록하고 참조 `doc:<문서 이름>`을 붙인다. 이미 이슈가 있으면 그 이슈에 같은 참조를 더한다.
- 기록으로 남기기만 하면 되는 한계(이미 받아들인 제약)는 등록하지 않는다.
- 이슈의 참조 `doc:`와 `issue:`는 대상이 서버에 이미 있어야 한다. 문서를 먼저 올리고 참조를 건다.

### 기록 문서를 쓸 때

서버는 올라온 기록 문서를 고치거나 지우지 않고 검색 색인에도 넣는다. 서식의 흔적이 남은 문서는 지울 수 없으므로 서식에서 파일을 만들고, 커밋하기 전에 검사한다. `agb doc new`는 `.agb.json`에 `new` 설정(서식 경로와 새 파일을 둘 폴더)이 있을 때 쓴다.

1. 서식에서 파일을 만든다.
   ```
   agb doc new <종류> --slug <slug> --title "<제목>"
   ```
   - `.agb.json`의 `new` 설정으로 서식에서 새 파일을 만들고 경로를 출력한다. 종류는 저장소가 서식을 둔 것만 쓴다. 종류 형식과 옵션, 채워지는 값은 `agb doc new --help`.
2. 남은 자리표시자(`<...>`)를 모두 채운다. 서식의 모든 `##` 절을 같은 순서로 두고, 절을 더하는 것은 된다.
   - 이전 기록을 통째로 대체하는 결정이면 `supersedes`에 그 문서 이름을 쓴다. 일부만 대체하거나 보완하면 `related`에 쓴다. 대체하는 기록이 없으면 `supersedes:` 줄을 비우거나 지우거나 `none`이라고 쓴다. 그 밖의 문서 이름이 아닌 글은 거절된다.
3. 검사한다.
   ```
   agb doc check
   ```
   - 인자 없이 부르면 새 파일이나 바뀐 문서를, 파일을 주면 그 파일을 검사한다. 검사 항목은 `agb doc check --help`에 있다.
   - Expected: 종료 코드 0. 1이면 출력된 문제를 고치고 다시 부른다.
4. 검사를 통과하면 커밋한다. 서버는 자리표시자 프런트매터가 남은 문서를 422로 거절한다.

### 기록 문서를 커밋한 뒤

1. `auto_sync`가 켜진 저장소는 `agb agenda`나 `agb issue comment --status done`이 커밋한 문서를 올린다. 곧바로 올리려면 다음을 실행한다.
   ```
   agb doc put <기록 문서 경로>
   ```
   - 파일은 읽은 그대로 올라간다. 이름과 메타데이터를 정하는 방식, 옵션은 `agb doc put --help`.
   - Expected: 종료 코드 0과 문서 객체(`name`, `state`, `sha256`). 서버의 경고는 stderr에 나온다.
2. 종료 코드 1이면 stderr를 읽는다. 오류 코드별 대처는 `agb help doc-format`에 있다.
   - 409 `immutable`: 서버에 같은 이름의 다른 원문이 있다. 파일을 고쳐 다시 올리지 않는다.
   - 409 `metadata_differs`: 같은 원문이 이미 있고 메타데이터가 다르다. 아카이브와 관계는 아래 "올린 문서를 고칠 때"로 고친다.
   - 422: 이름, 프런트매터, 참조, 크기 규칙을 어겼다. 파일을 고치지 않고 형식이 다른 문서는 인자로 맞춰 올린다(`agb help doc-format`).
   - 대처할 수 없는 거절은 최종 보고에 파일명과 사유를 쓴다.

### 작업을 멈출 때

1. 올리지 못한 기록 문서가 없는지 저장소 전체를 서버와 맞춘다.
   ```
   agb doc sync --root <저장소 경로>
   ```
   - 커밋했고 그 뒤 바뀌지 않은 파일 중 서버에 없는 것을 이름순으로 올린다. 서버에 있는 문서는 고치지 않는다. 출력 항목과 `skipped` 조건은 `agb doc sync --help`.
   - Expected: `conflicts`와 `rejected`가 비어 있으면 종료 코드 0이다.
2. 종료 코드 1이면 `conflicts`(서버의 같은 이름 문서와 내용이 다른 파일)와 `rejected`(서버가 거절한 파일)를 읽고 최종 보고에서 사용자에게 알린다.
   - 덮어쓰지 않는다. 파일을 고치지 않는다. 어느 쪽이 맞는지는 사용자가 정한다.

### 올린 문서를 고칠 때

고칠 수 있는 것은 아카이브 표시와 관계(`supersedes`, `related`, 이슈)뿐이다. 변경마다 문서의 활동 기록이 남는다.

```
agb doc archive <PROJECT> <이름>
agb doc unarchive <PROJECT> <이름>
agb doc link <PROJECT> <이름> [관계 옵션]
agb doc unlink <PROJECT> <이름> [관계 옵션]
agb doc activity <PROJECT> <이름>
```

관계 옵션은 `agb doc link --help`에 있다.

- 새 기록이 이전 기록을 통째로 대체하는데 올릴 때 `supersedes`를 빠뜨렸으면 `agb doc link <PROJECT> <새 기록> --supersedes <이전 기록>`으로 잇는다. 이전 기록은 대체됨이 된다.
- 폴더를 옮기거나 파일을 고쳐 상태를 바꾸지 않는다. 서버의 상태는 위 명령으로만 바뀐다.
- 종류, 날짜, 제목, 태그는 고치지 않는다. 틀렸으면 새 기록을 쓰고 `supersedes`로 잇는다.

### 작업 전에 과거 기록을 찾을 때

착수 전 정찰에서 작업과 관련된 과거 결정과 사고를 찾는다. 이슈, 댓글, 기록 문서를 한 번에 찾고, 찾은 항목에 연결된 결정과 이슈를 함께 본다.

1. 질문으로 찾는다.
   ```
   agb recall "<질문이나 핵심어>"
   ```
   - 통합 검색의 상위 결과마다 결정 그래프에서 바로 연결된 이슈와 문서가 붙어 나온다. 대체됨 문서는 이후 결정이 뒤집은 것이므로 새 문서를 읽는다.
   - `similar(0.82)`처럼 점수가 붙은 연결은 누가 적은 것이 아니라 내용이 비슷해 서버가 추정한 연결이다. 명시 연결보다 약한 근거로 보고, 원문을 읽어 관련 있는지 확인한다.
   - 결과가 없으면 핵심어 두세 개로 줄여 한 번 더 찾는다.
   - 범위와 필터 옵션, 출력 읽는 법은 `agb recall --help`.
2. 더 넓게 볼 때는 검색만 하거나 한 항목의 연결을 더 따라간다.
   ```
   agb find "<핵심어>"
   agb graph <KEY | PROJECT/문서 이름>
   ```
   - `find`는 지금 유효한 것(열린 이슈와 유효한 문서)만 찾는다. 닫힌 이슈와 대체됨·아카이브 문서까지 넓히는 옵션은 `agb find --help`.
   - `graph`는 대체됨·아카이브 문서를 접는다. 깊이와 상태 옵션은 `agb graph --help`.
   - 기록 문서만 종류, 상태, 가져온 문서 여부로 좁히려면 `agb doc search "<핵심어>"`를 쓴다(`agb doc search --help`).
3. 관련 있어 보이는 항목은 원문을 읽는다. `snippet`만 보고 판단하지 않는다.
   ```
   agb issue get <KEY>                 # 이슈
   agb issue activity <KEY>            # 댓글
   agb doc get <PROJECT> <이름> --content   # 기록 문서
   ```
   - Expected: 원문이 그대로 출력된다. `agb doc get <PROJECT> <이름>`은 상태와 관계를 보인다.

## 메시지 공간

`agb msg`는 프로젝트별로 짧게 사는 메시지를 넣고 읽고 지우는 공간이다. 이슈나 기록 문서가 아니다. 쓰는 방식은 쓰는 쪽이 정한다.

- 보내는 쪽은 넣고 돌아온다: `agb msg put -p <KEY> --to <라벨> --title "<제목>" --body-file -`. `--ttl`은 기본 7일이다.
- 받는 쪽은 읽고 처리한 뒤 지운다: `agb msg list -p <KEY> --to <라벨>`, `agb msg get <ID> --fields body --text`, `agb msg rm <ID>`.
- 기간이 지난 메시지와 지운 메시지도 서버에 남는다. `agb msg list --all`, `agb msg get <ID>`로 읽는다.

## 이슈 템플릿

모든 종류에 공통으로 지킨다.

- 서버가 에이전트의 이슈를 검사한다. 이슈를 만들 때와, 본문이나 종류를 바꾸는 수정에서 본문에 종류별 템플릿의 `##` 제목이 순서대로 모두 있어야 한다. 빠지거나 순서가 다르면 서버가 422(`body`)로 거절하고 빠진 제목을 알려 준다.
- 템플릿은 `agb template show <종류>`로 받는다. 이 절의 템플릿과 같은 내용이 그대로 출력되므로 파일에 저장해 채운 뒤 `--body-file`로 넘긴다. `agb template list`는 종류별 제목 목록과 제목 규칙을 보여 준다.
  ```
  agb template show feature > body.md
  ```
- 본문은 종류별 템플릿의 `##` 제목을 순서대로 모두 쓴다. 제목 이름을 바꾸거나 다른 제목을 더하지 않는다.
- 쓸 내용이 없는 칸에는 `없음`을, 확인하지 못한 칸에는 `미확인`을 쓴다.
- 확인한 사실과 추정을 구분한다. 추정에는 "(추정)"을 붙인다.
- 날짜는 `2026-10-17`처럼 절대 날짜로 쓴다. 다른 이슈는 키(`AGB-2`)로, 문서는 파일명으로 가리킨다.
- 제목에 다른 체계의 번호나 꼬리표를 붙이지 않는다. 관련 번호는 본문이나 참조에 쓴다.

### 기능 (`feature`)

제목: `<사용자>는 <무엇>을 할 수 있다` 형식으로 쓴다. 예: `사용자는 댓글을 최신순으로 정렬할 수 있다`

```
## 배경
왜 필요한지. 요청한 사람과 날짜, 관련 결정이나 이슈.

## 할 일
- 작업 단위 하나씩

## 완료 조건
- 확인할 수 있는 조건. 실행할 명령, 볼 화면, 받을 응답.
```

### 버그 (`bug`)

제목: `<위치>에서 <현상> 문제 수정` 형식으로 쓴다. 예: `PowerShell 파이프로 넘긴 본문에서 한글이 깨지는 문제 수정`

```
## 현상
기대한 동작과 실제 동작.

## 재현
1. 단계
- 환경: 버전, 인스턴스, 브라우저나 셸

## 원인
확인한 원인과 근거. 모르면 `미확인`.

## 완료 조건
- 재현 절차에서 기대한 동작이 나온다.
- 회귀 테스트
```

### 설계 (`design`)

제목: `<주제> 결정` 형식으로 쓴다. 예: `웹 정적 파일 서빙 방식 결정`

```
## 배경
왜 지금 정해야 하는지.

## 정할 것
- 질문 하나씩

## 후보
- 후보: 장점과 단점

## 제약
지켜야 할 결정, 규칙, 환경.

## 완료 조건
- 정한 내용이 명세나 원칙 문서에 반영되고 참조(`doc:`)로 연결된다.
```

### 아이디어 (`idea`)

제목: `<무엇> 검토` 형식으로 쓴다. 예: `로컬 서버와 운영 서버의 자동 동기화 검토`

```
## 내용
아이디어를 한두 문단으로.

## 출처
누가, 언제, 어떤 논의에서 냈는지.

## 검토할 것
- 채택 전에 확인할 질문
```

### 관측 (`observation`)

제목: `<대상>의 <현상> 관찰` 형식으로 쓴다. 예: `스테이징 DB의 시험 데이터 잔존 관찰`. `--recheck`에 다시 볼 조건을 넣는다.

```
## 현상
확인한 사실과 근거(명령, 로그, 수치).

## 지금 고치지 않는 이유
이유. 원문에 없으면 `미확인`.

## 다시 볼 때 할 일
- 재검토 조건이 되었을 때 확인하거나 할 일
```

## 지키는 것

- agb는 프로젝트의 이슈 트래커가 아니라 에이전트의 작업 기록이다. 작업 대상 저장소의 코드, 주석, 커밋 메시지, 브랜치 이름, 태그, PR·MR 본문에 agb 키와 agb의 맥락을 남기지 않는다. agb 키는 agb 안(이슈, 댓글, 기록 문서)과 기록 문서를 두는 저장소(`.agb.json`이 있는 저장소)에서만 쓴다. 커밋과 이슈는 작업 위치 댓글로 잇는다(3절 1, 5절 1).
- 필요 없어진 이슈는 사유(`--reason`)를 붙여 `cancelled`로 바꾼다. 취소에는 사유가 필수다. 잘못 만든 이슈(중복 등록, 시험 기록)는 사유를 붙여 지운다.
- 확인 표시(`agb issue ack`)는 사용자가 대화에서 확인했을 때("사용자 차례")와 에이전트가 대화 중인 사용자에게 보고하며 이슈의 키, 제목, 내용을 적었을 때(5절 3)만 한다. 사용자가 없는 세션에서 만든 이슈는 미확인으로 남긴다. `agb issue unack`은 쓰지 않는다. 에이전트가 만든 이슈는 미확인으로 시작한다. 미확인이어도 상태 변경, 큐, 막힘 계산에 영향이 없으므로 작업은 그대로 진행한다. 확인된 이슈의 제목, 본문, 종류를 바꾸거나 `review`에서 `doing`으로 되돌리면 서버가 미확인으로 되돌린다.
- `agb milestone create`는 사용자가 범위를 고른 뒤에만 쓴다. 범위를 고르지 않은 상태에서 마일스톤을 만들지 않는다.
- 활동 기록은 수정 요청마다 바뀐 필드의 이전 값과 새 값을 모두 남긴다. `agb issue activity <ISSUE>`로 본다.
- 스테이징이나 테스트 서버에 기록하지 않는다. 기록은 설정 파일의 서버 하나에만 한다.

## 접속할 수 없을 때

- 등록할 항목을 최종 보고에 모으고 사용자에게 알린다. 접속되면 등록한다.
- 서버를 직접 띄우거나 다시 시작하지 않는다.

## Windows

- Git Bash의 heredoc은 UTF-8로 넘어간다.
- PowerShell 5.1에서 파이프로 본문을 넘기면 셸 인코딩 때문에 한글이 깨질 수 있다. 본문을 UTF-8 파일로 저장하고 `--body-file <경로>`로 넘긴다.
- JSON 출력을 다른 프로그램으로 읽을 때는 UTF-8로 디코딩한다. agb의 JSON을 가공하는 스크립트를 쓰지 말고 `--fields`, `--text`로 고른다.
